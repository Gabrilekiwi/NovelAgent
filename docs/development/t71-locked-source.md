## 连续任务让出维护窗口

`JobSupervisor` 在每章开始前检查维护状态。已进入本章的执行仍按原路径完成、核验并保存结果和下一章游标；到下一章边界发现维护请求后，先确认子进程已经退出，再把任务保存为 `awaiting_input`。事件使用已有 `job.paused`，附加实际原因 `workbench_maintenance`、operation_id、已完成章数和 `automatic_resume=false`。不改写上一章提交结果，不将其伪装为作者主动暂停或 Provider 故障。结束维护不会自动续跑该任务，沿用显式 resume。

如果请求在首章预检开始前到达，保留原章游标且不启动进程。边界上的取消请求保存为 cancelled。仍处于 running 的章节不能被改成安全暂停；已进入 needs_recovery 的错误不被清除；活子进程阻止边界释放。

备份预检对“已认领但尚未生成日志”的首章有明确规则：只有最后一条合法维护暂停事件证明 completed_chapters=0、游标仍为首章、无结果时，才允许任务目录不存在。缺失或损坏事件不能充当“不需要文件”的证据。

## Windows 锁文件读取的实测修正

实际在本机持有 `.persistence.lock` 后，经第二个普通文件句柄读取该文件返回 PermissionError。若仍沿用普通清单/复制方式，持锁快照会在复制锁文件时失败；释放锁再复制又会丢失一致性边界。

`persistence_run_lock` 现在在持有原 OS 锁期间记录其拥有者句柄的只读能力，使用 ContextVar 保持同一执行上下文和嵌套恢复，进程/线程身份必须匹配。`held_persistence_lock_readers` 只返回当前活动能力。读取保留句柄原偏移并核对路径、物理身份、大小、mtime、单链接和普通文件类型；关闭、跨线程、伪造回调及硬链接均拒绝。一般锁函数的调用和原先返回的路径元组保持兼容。

文件清单/复制新增可选 `locked_readers`，锁文件从已持锁句柄读取，其他文件仍走原 SafePathResolver 和流式哈希检查，不排除锁文件，也不先解锁。独立 Python 进程在复制回调中争抢同一 OS 锁仍被拒绝，副本锁文件的原始字节一致。

## 组合来源上下文

`locked_backup_source` 在单一维护 capture 生命周期内取得：机器作品锁 → Provider 边界 → 自持整库事务 → 已存在 EA 全局锁 → 项目迁移依赖锁 → 本地持久化根锁。顺序兼容现有 publication 与项目 remap 的主要路径。已登记持久化根要求已有武装锁，不能静默重建丢失的登记锁；普通未武装的 Provider/依赖锁按既有锁组件初始化，随后才形成最终清单。

数据库锁内重新核对项目登记，已审核作品同时核验现有机器所有权。根据目录清单发现嵌入的 root_registry 控制根，持锁后重新检查根集合，预检使用这些锁句柄；上下文结束前再次核对所有作品/外部任务文件清单及机器所有权。调用方可在此上下文中完成整库 backup 和全部文件复制，不能只拿到一份清单后离锁复制。

此处已经验证 canonical Provider、迁移依赖、runs、reviewed/p 四类独立进程锁竞争。尚未据此宣称所有外部 CLI 命令和所有未知数据根均被完整覆盖；最终归档还需根与写入口审计、未知路径处理和完整历史认证。机器所有权仍位于副本之外，最终 manifest 需记录用于恢复交接的来源证明。
