# 回退后复用原归档的登记凭据链

日期：2026-10-02。阶段 D 内提前推进 T7.2。正向、拒绝和真实中断已有内部证据；当前代码 7 项针对性检查、51 项相关回归及原生 IAB 检查完成。Chrome 与默认 worker 验证仍待完成，完整恢复认证、正常格式升级和阶段 E/F 尚未完成。

## 问题与实现

原交接要求归档登记等于机器当前活动登记。一次正常回退会将原来源登记推进两代，即使作品身份、登记凭证和物理绑定均未变化，原归档也无法再次交接。原 7022 exit 1 在正常公共首次登记、再归档、实际复制/目录与数据库绑定、交接和回退后复现此问题，53.85 秒；第二目标的交接预览被拒绝。没有使用合成机器登记。

workbench/restore_rollback_ancestry.py 核对原交接意图、原回退决议和完成后的机器凭据。普通 V2 来源回退在实际原数据库写入隔离事务、作品状态及 Provider 边界内重新核对物理绑定、Strict 身份和作品凭证，保存 rollback-<活动记录摘要>-done.json。完成前损坏的既有凭据会在重新激活之前被拒绝。

workbench/restore_handoff.py 新增 machine_restore_handoff_v3：明确分别保存归档时的原登记、当前来源登记和完整回退链。预览和开始均重新读取实际机器证明；原动作续接、消费捕获、预算/任务/执行准备及启用通过原意图读取重新核对证明。交接 ID 与预览仍绑定当前来源记录、实际目标和恢复计划，旧预览不会沿用。

适用范围是同一 V2 原始登记：作品身份、登记 ID、作品凭证、原书和原数据库物理绑定完全相同，仅有可证明的回退代际推进。链最多 16 项，同时受 16 层递归及 32 MiB 大小限制；达到任一限制即拒绝。读取和预览不会补造丢失证明。CAS 后完成凭据尚未保存的真实中断，需明确续接原回退，重新核对原意图、原决议和实际原来源后完成。

V3 已恢复来源的旧归档复用，以及格式升级改变身份绑定后的旧归档恢复，仍需各自完整的资格续接/身份迁移证据。此次实现不赋予它们新的资格。所有诊断归档继续 recoverable=false。
