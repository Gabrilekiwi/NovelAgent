## 当前行为

`workbench/backup_certification.py` 引入 `RecoveryCertification` 和只读 `verify_recovery_certificate`。签发前重新执行真实完整归档组合核验，检查当前来源、快照 DB、配置和软件是否仍与归档相同；沿用原维护、机器作品、作品状态、Provider、数据库及持久化锁，不接受调用者提供通过结果或 `recoverable=true`。

证据为独立、原子创建的 `recovery-certificate.json`，不重写原 ZIP、manifest 或 completion。原包的诊断用途、`recoverable=false` 和原摘要均保留。内部认证结果是对不可变快照及指定恢复协议的附加证明；它本身的 `write_activation_allowed`、`automatic_provider_calls_allowed` 恒为 false，不能当成机器资格。

协议 `target_recovery_certificate_v1` 绑定归档完成 receipt、范围/DB/配置/源软件摘要、身份、真实数据核验摘要、源服务实例证据、独立验证器及 `windows_same_host_single_book_v1` 支持策略。策略保存当前支持入口族的实际源码哈希：工作台准入，生成/提交，身份/恢复，审阅/迁移，delivery/autonomy 和完整恢复步骤。它不是“任意脚本或任意外部根全部被覆盖”的声明。

当前明确要求同一软件构建：归档来源、签发器与复验器源文件指纹一致；未知跨构建兼容不自动放行。内存模块一致性仍未被证明。发布版本兼容与匹配版本回退必须继续由 F 阶段实际验证。

## 不可省略的条件

- 必须是已登记、活动的 Strict legacy 后端目标，支持身份格式 1.0/2.0/3.0；原活动记录、作品 witness、身份与原物理 DB 证据相互匹配。未登记归档不能成为升级许可。
- 当前所有已组合的离线数据检查、来源范围及续写条件必须通过，不能只检查 ZIP 完整性。
- 源版本必须有真实服务构造证据，并通过当前会话的未变检查。旧诊断包缺少新证据时不自动追认。
- 原包中没有辅助 store 时，不虚构一个辅助历史阻断；有 store 时由新的实际历史检查给出证明或具体阻断。当前已覆盖只保存过规划预览的完整根；delivery 和有 session/stage/completion 等其他控制历史的 autonomy 根仍报告 `auxiliary_history_not_certified`。原终态检查仍保留 false，不被擅自翻转或忽略。
- 当前支持的可写启用路径需要原来源和原机器控制文件保留，并核对归档后的最新用量；来源不可用或用量未知不得授权写入。只读离线复验不访问这些来源，也不替代该可写门槛。
- 认证前内容变化、凭据矛盾或被篡改，拒绝签发/覆盖。响应丢失后的明确重试可复验相同证据，已有相同认证文件保持原字节与物理身份。

这些条件是当前实现的限制，不能据此把完整计划缩成“只支持空历史或只读保全”。实际辅助历史覆盖、来源缺失时的恢复处理、完整产品验收仍须完成。后续公开升级还必须单独核对作者七类基线及其过期状态。
