# T7.1 受控备份：事实与实施检查点

日期：2026-09-11。状态：实施中，未验收；当前只有维护协调组件通过专项验证，尚未生成产品可恢复备份。

## 现状证据

主计划要求目标作品完整文件、必要runtime/模型与提交凭据、作者草稿、任务和预算、完整SQLite快照、非秘密配置及版本/哈希清单。其他登记作品只有数据库记录，没有随包文件，恢复时必须默认禁用。T7.0/D3实验不替代产品归档和最终T7.2恢复。

- `WorkbenchDatabase` 每个事务使用独立连接，`BEGIN IMMEDIATE`、WAL与FULL同步。后续需实际验证：持停写事务锁，同时使用独立只读源连接与新目标连接完成SQLite backup。直接在持写事务的连接上backup尚未验证，不作为已经可用的方案。
- `ReviewedWorkflow.mutate` 的顺序为机器作品所有权→Provider边界→数据库；它释放后两者执行实际操作，整个过程中保留机器作品锁。正式publication及budget也有明确所有权/Provider/DB边界。这些次序在备份取得锁时必须兼容。
- 网页改写入口分布在app及安装的chapter publication/budget路由，包含生成、提取、草稿编辑、确认、旧章纲与润色、任务和健康激活。许多调用使用`asyncio.to_thread`；HTTP取消不证明底层线程停止，因此不能仅按响应结束释放停写资格。
- `JobSupervisor._worker_loop` 会认领任务并运行子进程；执行会话可能跨多章。维护要覆盖认领、实际进程结束及收尾，监控失败或子进程未证实结束时不能释放资格。仅暂停polling或只修改jobs状态不成立。
- 后台任务日志在独立的`runtime_root/job_id/chapter_NNNN`，不一定在目标作品内。必须根据目标任务列出这些外部根，不能只打包书目录。未知的引用根阻止可恢复认证。
- app启动时planner/amendment及worker会本地恢复旧状态；维护中断后的重启应延后这些自动改写，待显式继续维护/恢复后处理。原本的实例OS锁及子进程继承能力应保留。
- `scripts/experiments/d3_restore_candidate.py` 仅覆盖隔离实验，不能直接开放到产品路径。产品备份/恢复仍需完整当前reviewed格式和多章历史验证。

## 本次已实现

`workbench/maintenance.py` 提供每个已持有InstanceLease共享的维护协调器。只读status不创建维护文件；admit登记实际写操作，begin先持久保存请求并拒绝后续admit，原操作可以完成。只有全部登记操作结束才允许require_quiescent/finish。异常退出后维护请求保留；新OS实例显示interrupted，不会自动恢复写入，显式resume原operation_id后递增代际。错操作ID、损坏记录、当前进程观察到记录丢失、失去实例所有权均拒绝。重复获取协调器共用同一活动集合，已结束的permit不能复用。

该组件尚未挂到HTTP入口和JobSupervisor，也不能独自保证文件/SQLite一致；不得将其状态quiescent等同于已认证可恢复备份。下一步必须覆盖所有实际写入口，并让许可覆盖线程/子进程的真实生命期，再按既有锁顺序完成快照预检和归档。需要将维护状态展示给用户并提供原操作的显式继续/退出；不得以超时推断写操作结束。

`tests/test_workbench_maintenance.py` 9项通过，包含真实线程收尾竞争、重建OS实例后的显式恢复、损坏/丢失记录、错误操作ID、异常释放及已关闭句柄。结果 `.tmp/stage-d-t71-maintenance.xml` / `.log`，1.01秒，命令exit0，无在运行的测试或服务。本次未改产品网页，无新的浏览器验收结论。
