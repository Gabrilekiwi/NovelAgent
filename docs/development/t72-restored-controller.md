## 要解决的实际问题

已启用恢复副本可以归档并通过底层协议恢复下一代副本，但原页面控制器原先明确拒绝再次恢复。仅删除该拒绝会使原实例在交出写资格后失去所有 API 访问和重启能力。底层恢复资格回退还会重新申请原页面已持有的实例锁，导致显式回退被自身阻止。

## 当前实现

- 已启用副本可以开始恢复维护、预览和创建会话。会话必须使用当前目标作品、原物理范围和原恢复来源证明的归档；旧代或其他作品归档拒绝。
- 交出资格后，依据实际原会话意图、目录绑定、原范围、归档来源证明、机器交接意图和当前机器记录识别原控制器。它只可访问原会话、原维护、目标核对和目标打开，不可开始新维护或新会话。
- 独立范围、SQLite 登记和物理身份仍先核验。原资格、原机器启用和本地准备凭据必须逐项与归档来源证明一致；损坏或丢失不会凭会话状态补造。
- 机器记录必须仍属于原交接的 restoring 记录、原启用记录或有原回退/续接意图的原回退记录；其他代际或操作拒绝。
- 正常 `load_restore_scope` 和 `WorkbenchDatabase` 默认继续拒绝被撤销来源。只有启动器和页面控制器明确请求控制范围；它保持 `read_only=true`，普通数据库连接和事务仍拒绝。`BookOwnership` 不借此取得写资格。
- 原控制器重启不执行任何恢复步骤、不启动 worker、不自动导入或调用模型；必须明确接管原维护和原步骤。
- 显式回退复用维护协调器实际持有且属于原数据库目录的 `InstanceLease`，保留机器、书稿、Provider 和 SQLite 围栏；其他目录或已释放锁拒绝。直接协议调用仍申请原实例锁。
- 以被撤销控制范围启动的实例完成回退后，保持原会话操作，页面要求重启才能重新进入普通写作；原本以活动范围启动的实例回退后可继续原访问。
- 页面先读取启动范围再加载项目路由。交接后显示原副本已交出资格、隐藏普通导航和诊断归档、自动选择原会话；原维护结束后仍不宣称恢复原副本写作。

上述控制范围只核验原有证据，不签发新写入资格；副本启用和原资格回退仍使用原底层协议。
