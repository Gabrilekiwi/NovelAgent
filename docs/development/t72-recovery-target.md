## 用户行为

恢复会话启用后，可以点击“打开已启用副本”。服务仅使用该持久会话绑定的目标，通过实际本机 `/api/instance` 身份验证复用已有实例，或使用本项目 Python 启动真实 `run_workbench.py --restore-dir ... --no-browser --port 0`。启动观察超时后保留原子进程，下一次显式打开继续观察；不根据超时推断进程已停止。

调用绑定原维护操作和最新会话状态摘要。调用者不能另传目录、URL 或写授权。实际恢复 CLI 取得自己的实例租约，关闭来源控制器不会成为目标实例已停止的证据。恢复 CLI 不自动导入作品或启动 worker。

正式正文使用原读取路径。保留的通用作者草稿通过单独的 `retained_author_draft` 字段和只读面板展示，核验项目、章号、修订和文本摘要；不自动作为正式正文、候选或已确认事实。字段仅包含草稿必要信息，不暴露归档来源路径。

## 已复现并修复的问题

来源控制器读取活动恢复会话时，会核验目标写资格。恢复目标每次 API 访问也核验同一机器写资格。实际两个进程并发读取时，普通 OS 锁竞争曾被包装为 `restore_scope_invalid`，导致维护状态 GET 409。原版本 12 组并发读取均出现一方 409；错误链直接记录 `RestoreScopeError → PersistenceLockError → PermissionError(errno 13)`。释放锁后接口恢复 200。原 Chrome 中两次 409 的旧响应体已丢失，不能声称已直接取得它们的错误链；本次证据证明相同接口存在这个真实竞争缺陷。

`PersistenceLockBusy` 区分普通非阻塞锁竞争与锁文件/句柄损坏。资格读取最多等待两秒，线程互斥和 OS 锁共用这一截止时间；取得实际锁后重新读取资格和凭据。超时返回 `restore_scope_busy`，不重建资格或接管其他实例。其他资格损坏仍立即拒绝。

扩展回归还暴露了已有同进程写线程等待问题：复制上下文的线程在原线程持锁时不应等待并借用执行权。默认写入在同进程和跨进程竞争下均立即拒绝；移除了所有权入口重复的无界线程等待。同一实际线程仍可按原句柄核验规则借用已持有的状态锁。
