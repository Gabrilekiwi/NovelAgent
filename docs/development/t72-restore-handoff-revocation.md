# T7.2：实际恢复副本的机器资格撤销与显式回退

2026-09-14。内部资格撤销、续接及回退组件已通过下述验证。没有开放恢复写入、升级、登记或恢复向导。

## 实际凭据与锁

新增 `RestoreHandoff`，输入真实归档包和已复制、已绑定物理根、已重绑定数据库的恢复容器。它核验原恢复计划、完整归档、全部恢复文件与历史、限定的 SQL 变更、数据库完成凭据和只读 scope；不接受调用者提供的“已验证”布尔值。

`prepare_restored_workbench` 增加内部借用实例锁和只核验模式。只核验模式要求完成凭据已存在、数据库已处于完整重绑定后的 SQL 状态，且没有 journal/WAL/SHM；不补造意图或 sidecar，也不替代未完成的恢复。原默认显式恢复路径继续保留原有中断恢复能力。

交接持有原机器资格锁、恢复容器实例锁、作品状态锁以及 SQLite 写围栏。归档内的原机器 v2 登记必须与当前 active 记录完全一致，恢复书内见证必须与登记一致。目标物理绑定从真实恢复数据库事务和 v3 身份取得。返回前再次核验整份恢复副本。正常运行中的恢复工作台实例会阻止此次内部交接；未来维护 UI 需要正式接入借用已有实例资格的服务路径。

## 状态协议

1. `preview` 计算绑定原记录、目标物理身份和恢复计划的确定性交接 ID，不写交接意图。`begin` 重新核验并要求原预览的 `intent_sha256`。
2. 在固定机器目录写 `handoff-<id>-intent.json`。此时源资格尚未撤销；此处强退后必须显式 `resume`。
3. 比较当前机器记录，写入原代际加一、绑定目标副本的 `restoring` 记录。原副本和目标副本的普通写入口均拒绝。随后持久保存撤销回执。
4. `resume` 核对原意图及实际目标，只接受原 source 或原 restoring 记录，不覆盖其他代际。重复完成保持同一回执和同一代际。
5. `rollback` 要求原根、原数据库物理身份、原登记、v3 身份链和书内见证仍成立，且原 Provider 边界锁已经存在。它先写回退决议，再比较当前机器记录，以再加一的代际恢复原绑定。目标仍只读，旧交接不能再次撤销原副本。回退决议已存在时可显式续接；决议丢失但记录已回退时不补造证明。

机器目录与记录在重要写入前后复查。恢复意图缺失不补造；机器记录丢失不重建；原目录不可用可以继续撤销原资格，但无法回退到不存在的原物理副本。仅恢复原路径名或复制数据库字节不能取得原物理资格。

## 后续约束

当前只完成交接的撤销及回退部分，返回 `target_writable=false`、`handoff_completed=false`。机器资格变为 restoring 不代表恢复已经启用；目标的只读数据库限制仍保留。

下一步必须处理预算、旧任务/旧准备计划和新执行目录，再建立目标 active 资格与可写 scope 的一致转换。机器登记代际不是章节内容或模型消费账本的修订号；不能以机器记录未变为依据，假定归档后没有新的消费。若原副本不可用，归档之外无法核实的消费仍须保留为未知，不能通过载入旧账本清零或重新获得预算。源数据没有被此次资格撤销覆盖，但这不替代预算核验。

当前交接仅支持已有 v2 见证的登记作品和最终 reviewed 格式的真实恢复副本。旧 v1、未登记 legacy 升级前备份以及所有证明丢失的情况尚未由该组件解决。正常旧书接入、升级前备份恢复和最终格式恢复均须纳入完整认证，不能只以本组件的 reviewed 用例给全部备份标注可恢复。

恢复后零自动调用、实际下一章续写、恢复来源的再次备份、正常旧书升级/登记入口及恢复向导仍待；T5.2、阶段 E 和真实 T8.1/T8.2 也未完成。完整 A–F 目标保持不变。
