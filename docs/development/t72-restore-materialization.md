# T7.2 实际解包与中断边界

日期：2026-09-14。已验收的是实际复制到新目录的底层服务，以及复制中断后阻止普通启动的边界。**没有完成 T7.2 可写恢复，不代表阶段 D、F 或完整 A–F 已完成。**

## 当前实现

`workbench/backup_restore_materialization.py::materialize_archived_restore` 接收已保存的计划，但执行前仍重新运行完整归档核验与位置规划，逐字段核对归档凭据、磁盘实现版本、目标和父目录绑定。调用方修改标志并重新计算摘要，也不能绕过重新核验。

目标必须是独占新目录。任何数据库字节写入前，先持久化 `restore-intent.json` 和原计划。原数据库、书目录、书内或书外任务资料目录逐成员流式复制、刷新到磁盘、写后核对；文件、目录、物理身份、清单和控制文件内容在结束时再次检查。归档读取上下文的退出校验通过后，才发布 `restore-materialization.json`。

整份数据库字节与逻辑摘要保持原样，包括其他作品登记；目标登记的旧路径在本步骤也保持原样。旧 registry、manifest、回执、正文、作者资料和模型证据不重写。Windows 路径预算包含恢复控制文件，不能只检查包内书文件。

失败保留部分目录，不能覆盖重试。恢复意图使缺失、部分复制或复制完整但尚未绑定的数据库无法作为普通工作台启动。当前完成凭据只表明 `materialized`，明确保持 `database_rebound=false`、`new_physical_controls_installed=false`、`read_only_app_ready=false`、`restored=false`、`recoverable=false` 和 `write_activation_allowed=false`。

此底层服务尚未接入恢复向导。它没有取得同机所有权、没有重定位 SQL 中的目标/任务路径，没有提供迁址后的权威历史读取，也没有恢复旧任务或执行下一章。不能拿本页的复制完成凭据作为启用授权。启动隔离依赖保留的恢复控制资料；本轮不承诺防止手工拆散、移走或删除全部控制资料后运行任意历史程序。
