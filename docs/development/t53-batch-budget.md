# T5.3：批次统一预算内部组件

2026-11-04。本轮将批次金额、调用数和输入/输出 token 上限接入原模型调用预留与发送路径，并补充归档和恢复检查。**预算就绪不等于批次执行授权。** 公开批次配置/授权、策略审核来源和自动修复/连续提交尚未安装，整个 T5.3/T6 和 D/E/F 未完成；真实 Provider 调用、真实作品写入及新增正式接受均为 0。

## 冻结条件与原账本

batch_budget_v1 支持同一作品 1–64 个连续且不重复的章号，各章须已有完整的显式价格、金额上限和同一币种；批次另外冻结金额、调用、输入/输出 token 上限。缺价、币种不同、其他作品、章号缺口、布尔数值及非规范哈希均拒绝。没有汇率换算。实际生产模型能力仍由原请求/计价协议核验，本轮测试全部使用合成价格和响应，未核对账户账单。

批次消费直接汇总各章 ledger.json 内的原预留/发送/Receipt，不维护第二份可变总数。生成、修复、事实提取共用这些原调用。章账本只有在明确绑定批次时升为 v4，冻结原 batch_id、batch_budget_sha256 与单章预算 SHA；原 v2/v3 不自动修改。单次修复资格可在 v4 中持久化，不能丢失批次绑定或使用其他批次的资格。

每次新增预留先取得作品预算 coordinator，再取得本章账本锁，核对整个批次的现存消费及下一次调用的保守预留。任何一章存在未解释的预留或发送状态，批次都不开始新增调用；未知费用继续占用。金额或调用/token 上限不足时，原账本留下带 batch_ 原因的本地拒绝，运行时发布未发送凭据，Provider operation 为零。正式发送前再次核对原批次记录及上限。普通 ChapterBudgetStore 也执行同一逻辑，不能通过另造 runtime 适配器绕过批次约束。

结算仍由原 runtime 核验已持久化的实际 Intent、响应和 Receipt；没有第二份结算，恢复不把归档总数再加一次。活跃区间及单章时间预算沿用原服务路径；本组件没有新增批次自动执行器或批次时间口径。

## 初始化、丢失与恢复

显式 freeze 在调用方作品所有权和 Provider 排他边界内进行，before_write 负责核验真实作者授权及当前来源/选择。内部存储回调或预算哈希本身不构成授权。

初始化先保留不可变批次清单，再建立/核对原章预算和 v4 绑定，最后发布 ready 凭据。部分初始化会阻止新增调用，必须显式续办同一清单；不能改价、换章或用新批次复用原章。已发生调用、修复资格消耗或主动执行时间的章，不能被事后接到新批次；该拒绝在新批次 Intent 发布前执行。

批次清单/ready/本章绑定丢失均不能当成“没有批次限制”。仅删除 ledger 中的绑定并重新计算哈希也会被原清单拦截。离线用量检查同时核对归档中清单、ready、各章原预算和绑定；不打开活跃源或初始化 runtime。恢复要求原绑定保持不变，且原清单/价格等不可变文件完整；金额相同的合法 v2 独立快照仍不能覆盖已有 v4 批次归档。保留了所有现有源不可用/用量未知的可写恢复限制。

新增代码：core/batch_budget_contract.py、core/batch_budget_store.py。接入 core/chapter_budget_store.py、workbench/model_usage_budget.py、workbench/model_usage.py、workbench/backup_archive_usage.py、workbench/backup_scope.py、workbench/restore_budget_merge.py。没有公开批次入口或新的后台付费行为。
