## 3. 实用性与产品定位

目前价值最清楚的能力是：

- 正文与状态一起提交，防止正文已变但记忆未更新。

## 5. 技术实力与路线判断

### 应保留的技术

Python、FastAPI、SQLite 与 Windows 本地单作者场景匹配。事务中使用 read-set、hash/CAS、提交标记和恢复语义，模型调用有持久化 Intent/Receipt，SQLite 使用事务与 WAL。这些是真实工程能力，不是包装出来的“Agent”概念。[模型调用](D:/Pycharm/PythonProject/NovelAgent/core/model_call_runtime.py:367)、[事务提交](D:/Pycharm/PythonProject/NovelAgent/core/engine/persistence.py:380)、[工作台数据库](D:/Pycharm/PythonProject/NovelAgent/workbench/database.py:100)

核心能力是确定性编排与状态管理。模型负责创造候选、解释和提议，程序负责验证结构和决定何时写入；作者负责选择剧情及判断可读性。这个分工合理。模型升级可能提高生成和抽取能力，但不会自动补齐提交闭环、费用核账和验收方法。

### 需要收敛的技术

当前 core/modules/api/workbench 共 203 个 Python 文件、115,527 行，另有 129 份 schema；不含 scripts/tests/static。执行器 5,351 行，工作台 jobs 4,270 行。体量不能单独证明代码质量差，但多条执行、状态、迁移与恢复路径已带来显著维护成本。

普通执行默认仍是 legacy runtime；持久化 StoryProject 写回默认 standard 并开启确定性 Review，LLM 验证不在所有路径上强制启用。strict、事件权威、autonomy、执行 Shadow 等是不同维度，不能把它们合并称为“已默认全自动”。[质量策略](D:/Pycharm/PythonProject/NovelAgent/core/engine/quality_coordinator.py:24)

建议近期冻结通用自治扩展、执行框架切换、任意项目迁移和新状态体系。先复用现有事务底座接通一条作者流程，再根据重复代码和维护成本做局部抽取。没有证据要求现在换语言、引入微服务、向量数据库或换 agent 框架。Anthropic 的一手工程经验同样强调先使用可评估的简单编排，增加复杂度应有任务收益支持。[官方工程说明](https://www.anthropic.com/engineering/building-effective-agents)

### 新路线值得验证，但还不能宣称优越

当前新增的流程是“单次正文候选 → 独立提取事实 → 作者确认”，有望降低模型同时写小说、补齐状态结构、计算数量并保持场景契约的负担。[候选生成](D:/Pycharm/PythonProject/NovelAgent/core/engine/chapter_candidate.py:437)

但收益只是合理假设：整章生成可能带来长度控制和长程一致性问题，人工逐条确认事实也可能增加负担。应把它作为同模型对照试验的候选路线，记录审核事实的耗时，只把关键变化或有歧义事实交给作者复核，不能用增加确认按钮代替效果验证。

建议形成唯一正式链：

```text
作者确认章节意图
  → 生成正文候选
  → 作者编辑并选择正文
  → 提取带原文证据的事实建议
  → 确定性检查与必要的作者确认
  → 编译为现有状态补丁/事件
  → 复用现有章节事务提交
  → 正文与状态读回
  → 下一章读取已确认版本
```

数据完整性、重复扣写和明确事实冲突继续硬阻断；文学风格、节奏及模糊叙事判断以建议为主，让作者有明确决定权。这样既保护正式状态，也减少正文为了满足验证器而反复解释规则的压力。后一种因果关系仍需对照试验验证，本次只能确认重复文本和规则约束同时存在。

## 8. 建议的推进顺序与验收条件

### 第一步：把当前路线收成一条闭环

先修事实提取契约，接通作者确认后的正式事务和下一章读取。同时处理单实例启动、费用未知提示与一致备份。完成标准是：一个隔离项目可以从章节意图走到正式正文和状态读回；中断、刷新、重启不丢作者修改，不重复提交，不自动重试不确定调用。

这一步保留当前可靠性设施，不要求重写引擎。报告发现项本次未修复，后续开发应以此为具体任务清单。

### 第二步：验证是否真的节省作者劳动

先做小规模、冻结条件的同模型对照：相同章纲和已有上下文，一边使用工作台，一边由作者手工管理同一模型的写作过程。保留原稿、修改稿、所有失败和实际费用；阅读时隐藏来源、随机顺序。如条件允许增加独立读者，避免只由开发者评分。

最关键指标是“获得一章作者愿意使用且可继续的正文，总共花了多少人类时间和钱”。人类时间包括准备、阅读、编辑、确认事实、排错和恢复；API等待单独记录。不要只测点击生成后的速度。

建议先用三个章节任务发现方向性问题，约定一个有意义的节省目标，例如在可读性不下降且没有严重连续性错误的前提下，总主动用时减少至少30%。这个数值是待协商的产品决策阈值，不是现有成绩；三章样本也不能证明统计显著性或长期稳定性。

### 第三步：通过后再推进连续生产验收

沿用已有较严谨的十章门槛：事务和readback完整、首次通过率、修复次数、阅读均分、编辑时间、后期衰减和预算。使用明确连续范围，失败和中途改代码导致失效的记录全部保留。已经过时的23–42章固定编号需要在新基线下重新安排，不能覆盖正式历史或拼接成功章节宣称通过。

### 第四步：根据结果决定扩大范围

只有当时间和质量收益在更多作者/作品中复现，再投入公开安装包、更多题材或云端协作。若复杂路线不能胜过更简单的作者配合模型流程，应该删减无收益的生成/审核环节，保留确有价值的记忆、版本、恢复和提交能力。
