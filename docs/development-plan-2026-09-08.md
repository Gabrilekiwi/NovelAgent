# NovelAgent 稳定自用版开发计划

制定日期：2026-09-08。依据：[2026-09-07项目审查](D:/Pycharm/PythonProject/NovelAgent/docs/project-review-2026-09-07.md)。

**主攻目标：让已有作品在一个共用的章节流程中，既能逐章审核提交，也能按批准章纲连续生产；正文、事实和下一章上下文一致，异常可恢复，成本可解释。**

本文件是开发计划，不表示功能已经实现或真实生产验收已经通过。

## 1. 已确定的目标、范围与决策

用户已经明确选择：

- 近期交付稳定自用版，运行环境为 Windows 本机单用户。
- 同时交付“逐章审核”和“连续自动”两种模式。
- 连续自动模式允许一次预算内自动修复，未通过时暂停。
- 首版优先覆盖已有作品，完整从零建书引导安排在后续版本。
- 真实模型调用与人工阅读是独立验收阶段；实现和本地验证不包含默认付费调用授权。

两种模式共用候选生成、事实提取、检查、提交和恢复服务。模式只改变批准范围、暂停节点及审核决定来源，不维护两套新的正文执行引擎。默认选择逐章审核，自动模式由作者为有限章节范围显式启用。

当前目标书仍为 **legacy Strict**，不是事件权威模式。保留其书籍身份和正式历史，首版不得以强制迁移到 event authority 作为使用条件。已有 event-authority 项目走对应后端；适配层区分数据来源，共享上层流程。

保留 Python、FastAPI、SQLite、现有目录及事务/凭证设施。本轮暂缓公网 SaaS、多人协作、移动端、模型训练、向量数据库、通用 Agent 框架替换、完整历史剧情重写和全面新书向导。

完成信号分两层：

1. **工程候选版完成**：两种模式的完整闭环、故障恢复、预算、备份和 Windows 安装验证通过，可进入真实验收。
2. **稳定自用生产版成立**：独立真实验收也通过；不能仅依据工程门命名为已验证的稳定生产版。

## 2. 优先级与依赖

当前主要矛盾是：已经拥有较多可靠性模块，但作者实际工作流尚未闭合、效果未充分验证。这属于技术与资源的可协调取舍；先完成同一条章节闭环，再用共享策略提供自动化。需要持续监控事实审核负担是否抵消节省的编辑时间。

不按自然日承诺交付日期，避免额度中断使排期失真。每个工作包按下列独立验收项拆成可提交的小任务，完成当前任务后再进入下一项。

## 3. 各工作包的实现与验收

### T0：保存开发基线，建立可中断的执行方式

- 保留全部现有修改，整理当前候选、事实提取、审核功能为可回退的代码基线。按功能分组提交，排除密钥、正式书稿、运行数据库及临时产物；不直接进行整库 `git add .`。
- 开发任务记录固定包含：目标、范围、验收条件、当前提交、改动文件、已运行检查及结果、剩余工作、下一条操作、活动进程/端口和付费调用状态。
- 本计划使用稳定任务编号T0–T8。阶段结论放入版本管理内的文档；大量原始测试产物继续放在隔离目录，通过路径与哈希引用。
- 当前基线证据是1905项测试、561项子测试通过，8项跳过，本地smoke通过。它只对上次审查工作区有效；开始时检查差异，不无条件重新跑完整审查。

验收：恢复另一轮开发时，仅凭任务记录即可知道下一步；没有“已完成”但缺少证据的标记；原有工作无丢失。

### T1：先修复可独立完成的本地运行问题

- 在初始化数据库、恢复任务和启动worker之前，取得以工作台数据目录为范围的进程持有排他锁；锁维持整个服务生命周期。
- 第二次启动读取首实例的本机地址，核验实例标识后打开已有工作台并退出，不再换端口启动共享数据库的第二个worker。其他应用占端口时，仍允许首实例选择其他端口。
- 锁由操作系统随进程死亡释放；保留的元数据不能被当作存活证明。无法确认实例状态时显示诊断，禁止接管仍可能存活的任务。测试实例使用各自独立的数据目录。
- 将不存在的保存父目录、非法路径等预期输入错误转换为结构化4xx和中文提示。表单明确要求选择已有父目录；保留已输入的作品信息。

验收：两进程同时启动仅一者拥有worker；重复启动不改变running任务；首实例异常退出后重启进入既有恢复分类；非法目录不再返回500，合法目录建书成功。

### T2：补全事实契约，建立可审查的事实准备流程

- 为event、character_state、relationship、roster、location、inventory、counter建立同源契约：模型请求包含所有必需字段、合法操作值和各类示例；本地解析与界面验证复用同一契约。兼容端点不支持结构化输出时也必须收到完整契约并接受同样的本地检查。
- 事实必须绑定当前正文修订、哈希和准确原文范围。正文修改使旧提取/审核过期，旧记录保留，不转移旧确认结果到新正文。
- 逐章模式允许逐条接受、修改、拒绝和显式批量确认；作者可补充模型漏掉的事实。新增事实记录单独的来源，不允许覆盖模型原始建议或伪造其证据。
- 支持角色、地点、物品的最小实体声明和同章引用。稳定ID由程序分配；已知别名复用现有身份；重名、多义、意外新实体进入人工处理。自动模式可使用章意图中已经批准的实体声明，不能擅自把新实体当已有实体。
- 数量、库存、名单、关系等缺少起始定义时显示“基线缺失”；有明确来源或作者确认后才初始化。不得默认库存为零或根据模型猜测创建事实基线。
- before值、数量计算、事件ID和引用依赖由程序从可信状态生成。同目标的多次变化按明确证据顺序归并；顺序不明或相互冲突时阻断。拒绝事件后，其依赖事实不能继续被接受。
- 增加内容一致性检查结果，覆盖语义重复、场景衔接、动机/对话提示和事实遗漏；复用现有LLM验证能力，结果绑定终稿哈希。输出具体问题与证据，不将机器总分直接称为文学水平。

验收：七类混合事实均能从契约生成合法请求并解析；新实体同章引用与下章读取成立；重复事实、无来源数量、拒绝依赖、改稿后旧审核均被拦截。漏抽事实能够由作者补齐，不要求编辑JSON。

### T3：接通正式提交，确保旧书真实可用

从现有executor中抽取有限的共享“准备发布/提交/核验”服务，复用已有校验器、Memory事件构建、事务及发布凭证。工作台不直接调用executor巨大私有方法，也不绕过事务自行写正文。

统一输入是正文最终版本、事实决定、可信上下文和提交授权；统一输出是可预览的变更与提交计划。提交计划绑定项目、章号、正文/审核修订与哈希、read-set、后端权威版本和幂等键。

**legacy Strict兼容必须作为本工作包的主体，而非附带项：**

- 旧`prepare_chapter_memory_commit`显式不采用authoritative_state_delta，旧受管字段也不覆盖全部七类事实。因此不能只传入一个delta就声称完成兼容。
- 在现有StoryProject受管内容中保存经验证的结构化状态，扩展语义读取、输入包映射与事实上下文，使七类事实能从项目文件重新构造。复用现有authoritative-state字段模型；不另建独立权威数据库，也不把SQLite或旧runtime缓存提升为事实来源。
- 保留原手写设定和非受管内容。遇到同一事实的相互冲突来源，展示差异并等待作者决定，不能静默覆盖或双重计入。
- 项目采用新字段契约需要备份、兼容预览和显式启用；标记所需reader/writer能力版本，旧版本必须拒绝写入。语义/parser版本变化按真实兼容检查处理，不修改版本号或伪造校准报告来绕过Strict门槛。缺少有效校准时只提供预览，正式启用留到目标书验收准备。
- event-authority适配器继续以回放投影为基线，复用现有事件批、恢复屏障和发布凭证；不改变其权威语义。两后端只比较共有领域状态与正文结果，不要求内部事件表示完全相同。

提交先规范化最终正文，再验证引用与哈希。只允许写下一未提交章；历史正文仍使用既有修订机制。正式正文、状态、章游标、运行记录及必要提交证据进入同一现有事务边界；SQLite中的提交结果是索引，成功判据来自后端凭证和readback。

验收：

- 在legacy Strict和event-authority隔离样本上，七类状态变化与正文一同提交；关闭进程、移除可重建缓存后，下章仍读取正确状态。
- 草稿修改、权威头变化、手写文件变化、章号已存在时拒绝过期提交。
- 双击或重复请求只产生一个逻辑提交；幂等键复用但内容变化返回冲突。
- 提交前崩溃不推进章节；提交标记后崩溃完成原事务恢复；正文已落盘而SQLite尚未更新时可根据凭证重建索引，不再生成一次。
- 空事实集不能自动等同于“无事实变化”；需明确检查结果或作者确认。

### T4：交付逐章审核的完整网页流程

串联现有章节意图卡、候选、编辑、事实提取与T3提交服务，统一为可恢复的单章任务。界面继续使用现有五个主区域，不增加一套平行工作台。

作者流程：选择已有作品 → 确认章意图 → 生成 → 审读/编辑 → 检查正文及关键事实 → 预览将提交的内容 → 确认提交 → 进入下一章。生成中的候选、作者草稿、检查结果、已提交正文必须有清晰标识。

正文、事实和提交的进度由后端状态驱动。长调用通过既有任务/事件机制展示，刷新不丢进度。用户暂停后保留人工提交确认；不存在用户确认的请求不得伪装为已审核。已批准草稿不会被后台任务覆盖。

验收：从网页完成连续两章的确定性隔离演练；分别在生成后、编辑后、检查后、提交中断点重启；不查看运行JSON、不手工搬草稿、不使用恢复CLI也能完成任务。

### T5：建立费用口径与真正的执行预算

- 每个物理Provider attempt保存调用阶段、模型/端点标识、输入/输出用量及来源。区分已核对费用、依据价格估算的费用、未知费用；旧记录中没有依据的零值在界面显示为未知，保留原始历史值。
- 价格配置按provider/endpoint/model绑定，包含币种及计费项，冻结到本次任务。兼容端点不能套用官方价格；不自动抓取或写死可能过时的价格。缺少价格时逐章模式可以显式选择token/调用数限制，但不能宣称有金额止损。
- 自动模式必须有可解释的价格配置、单章和批次金额上限。批次统一币种；首版不做汇率换算或自动支付核账。
- 调用前预留输入估算及最大输出成本，响应后按已知用量结算。失败或状态不确定调用保留预留额，不能当作免费释放。价格或用量不可解释时停止自动生产。
- 生成、提取、独立检查、修复和重检共享章节预算，章节恢复和点击重试不刷新预算。当前默认调用/token/时间上限继续作为独立硬限制；不额外增加弹性金额。
- “周预算”继续作为统计项；执行中真正约束的是冻结的单章和批次预算。界面明确预算是本地估算控制，最终账单以Provider核对为准。

验收：用假Provider验证调用前超限不发请求、缺价格不启动自动批次、失败尝试不漏记、恢复不重复扣记/清零、同批次修复计入总额、多币种配置被拒绝或拆成不同批次。

### T6：在相同流程上加入连续自动和一次修复

- 批次开始前冻结连续章号、批准章纲、模型/配置、预算、自动策略版本及代码基线；下一章只在本章提交和readback完成后启动。不得并行生成依赖前章状态的章节。
- 自动通过需同时满足：确定性事实检查、正文/状态一致性、独立语义检查、有效预算、无未确认身份、无不确定调用。轻微文风建议进入历史，可继续；严重重复或连贯性问题视为可修复失败。
- 对明确可修复的正文/提取格式/连贯性错误，最多一个修复周期；修复范围由具体问题决定。修改正文后重新提取受影响事实并完整重检最终状态，不能沿用原稿审核证据。
- 一个修复周期包含所需修复、提取和重检调用，全部计入原章节/批次预算；修复次数持久化，刷新、重启、恢复不能再次获得一次额度。
- 身份/数量基线未知、事实来源冲突、read-set变化、哈希损坏、事务未恢复、Provider状态不确定和预算不足直接暂停，不能交给模型猜测后自动放行。
- 自动模式的接受来源记为`policy`，保存策略版本及批次授权；人工接受记为`author`。不把策略接受写成`author_confirmed=true`，也不修改旧的人工确认凭证。
- 异常进入与逐章模式相同的编辑/确认入口。作者处理后可明确提交并继续原批次；模式切换只在章边界或暂停状态生效。暂停和停止沿用已有语义，服务重启后不会擅自发起新的付费调用。

验收：正常三章自动提交；第二章首次失败经一次修复通过；第二章修复仍失败则暂停且第三章未调用；人工处理后继续原批次；进程在修复过程中中断后不会重置次数；相同最终正文和事实在两种模式下产生相同领域结果，审核来源记录不同。

旧生产任务保留查看和恢复入口，新的工作台任务接入共用流程。已开始的旧任务绑定其原执行版本，不中途改引擎。新契约启用后的作品不能再由不支持该契约的旧路径写入。

### T7：补全备份、恢复和可重复发布

备份以完整本地工作台为首版范围：SQLite一致快照、已登记作品、必要runtime/凭证/作者草稿/批次状态以及版本与文件哈希清单；用户可先查看涉及目录与体积。不把TXT导出或单个事务before-image称为完整备份。

- 进入维护状态后阻止新任务和编辑写入，等待已有写操作结束，按固定顺序取得数据库/项目/提交锁；使用SQLite backup API，不直接复制活动WAL文件。
- 有进行中Provider调用、未完成事务或未知可变外部根时，拒绝标记为可恢复快照，显示具体待处理项。升级前保留备份；不自动删除已有备份。
- 归档排除.env和凭据，保留运行需要的脱敏配置。配置密钥由作者在恢复机器重新提供。
- 首版提供恢复到新的空目录及隔离数据目录的演练；不覆盖现有正式目录。保留书籍逻辑身份和不可变历史，恢复副本在核验完成前不能启动worker。
- 当前remap只接受保留目录身份的同卷重命名，不能用于解压复制。单独实现受恢复清单约束的root重新绑定：只更新可变的注册/恢复元数据，旧的哈希历史保持不变并保留来源映射；无法解释的根或凭证拒绝启用，不靠批量替换绝对路径修复。
- 恢复后核验正文、权威状态、事件头/凭证、作者草稿、队列位置和预算。新物理位置使进行中的准备计划失效，需重新准备；已提交结果只核验，不重发模型调用。恢复实例不得与原实例同时写同一本逻辑作品。
- 增加可重复依赖锁和Windows CI；启动器优先项目虚拟环境，校验Python版本与依赖；保留Ubuntu回归。测试中文/空格路径、双击启动、重启和升级失败恢复。

验收：含作者未提交修改的完整隔离工作台可以备份并恢复，内容与状态一致，恢复后零自动Provider调用；损坏归档和未知根被拒绝。干净Windows环境按文档安装启动，不依赖开发者全局Python。

## 4. 重要接口与兼容约定

以现有API风格增加最少接口，不更换前端框架或任务系统。

| 接口/类型 | 用途与约束 |
|---|---|
| `execution_mode = manual_review \| auto` | 新任务选择审核策略；默认manual_review；既有任务保留原执行版本 |
| `review_source = author \| policy` | 新版本审核决定明确来源；旧确认记录保持原语义、哈希和不可变性 |
| `ChapterCommitPlan` | 纯准备结果，绑定正文、事实、read-set、权威版本、变更预览、校验结果；不是新的状态系统 |
| `POST /api/projects/{id}/chapters/{n}/commit-preview` | 无模型调用，重新校验当前草稿/决定，返回提交计划及阻断原因 |
| `POST /api/projects/{id}/chapters/{n}/commit` | 接收计划绑定和幂等键；再次验证后复用正式事务，返回状态和凭证引用 |
| 任务状态、提交状态查询 | 复用既有jobs/events查询；提交后DB索引可由正式凭证修复 |
| 费用配置与预算摘要 | 按模型端点保存非敏感价格及币种；摘要区分actual/estimated/unknown和预留额 |
| 本地备份/恢复任务 | 异步任务提供预检清单、进度、哈希核验和恢复预览；不得当作任意路径覆盖API |

工作台数据库采用递增版本、增量迁移、迁移前备份。新事实契约和审核来源使用版本化读取，不重写旧artifact来迁就新schema。legacy与EA后端复用相同作者流程，但各自执行已有权威验证规则。

## 5. 测试、工程门与独立真实验收

### 工程门

日常以当前工作包相关的单元/集成测试为主；T3、T6、T7交付点再运行完整pytest和本地smoke，避免无变更重复跑全套。跳过项和平台限制必须单列，不能计为通过。

浏览器验收使用独立数据库、隔离作品和确定性Provider，检查实际操作、console、network及重启状态。至少覆盖逐章两章、自动三章、一次修复转人工、错误目录、重复启动、预算暂停、备份恢复。

**工程候选版必须同时满足：** T0–T7全部完成；两后端支持的事实均可完整读回；两种模式使用同一正式提交链；无已知丢草稿、重复提交和不确定调用自动重发问题；全部相关检查通过，限制明确记录。

### T8：独立真实验收

用户单独安排Provider、费用上限和阅读时间后再执行，工程交付不因此默认获得真实调用授权。

1. 使用当前目标书当时的最新只读状态建立隔离验收基线，核验旧失败和待恢复状态，准备有效Strict/契约资格；不覆盖第1–26章，不默认清理第27章失败证据。
2. 冻结代码、依赖、模型、端点、价格、预算和章纲。先做有限Provider smoke及一章完整验证，记录实际用量和费用来源。
3. 三个章节任务做同模型对照：工作台流程与作者手工管理同一模型使用相同输入；随机阅读顺序，记录九维评分、所有失败、编辑/事实审核/排错主动时间和等待时间。工作台三任务至少各覆盖一次逐章、一次自动及一次人工接管。
4. 方向性通过条件：没有严重事实缺陷，阅读质量不低于对照，主动时间目标至少减少30%，费用在预定上限内。这是产品决策阈值，不声称三样本足以证明统计显著性；不达标先分析原因，再决定删减或修复环节。
5. 小样本成立后，固定两个连续十章批次；第一轮主要验证逐章审核质量，第二轮主要验证连续自动与异常处理。范围按当时最新正式章号顺延，不使用过时的23–42固定编号，不在同一逻辑作品创建可同时运行的重复副本。

两轮沿用现有主要标准：10/10正式提交与readback；无严重缺陷/未解释内部错误；首次检查通过率至少70%；每章自动修复最多一次；九维平均至少3.8；至少8章总体可用性≥4；编辑时间中位数≤20分钟、P90≤30分钟；后3章均分相对前3章下降≤0.3；费用不超冻结预算。

逐章模式的例行审读/确认不计为“异常流程介入”，但全部计入主动时间。自动模式最多两章需要额外人工接管。模型审查分与人工分分别记录，不能互相替代。任何正式验收期间的代码/模型/章纲变更都使该批失效，失败记录保留。

只有工程门与T8都通过，才标记稳定自用生产版。随后再规划从零建书、小范围其他作者内测和大规模性能优化。

## 6. 额度中断与执行纪律

- 同一时间一个主攻实现任务，最多一个边界清楚的辅助审查；不反复派多个代理重读全库。
- 每个小任务完成后记录实现、验证、剩余限制和代码提交。预计可能中断前保存未完成差异、运行中的测试/服务及下一操作，不把“正在跑”写成“已通过”。
- 恢复时先读[开发交接记录](D:/Pycharm/PythonProject/NovelAgent/docs/development-handoff.md)，核对Git差异与任务结果，再继续。已结束的测试不重复；运行中的任务先检查状态，不能启动第二份。
- 任何真实Provider状态不确定都先分类，不能因额度恢复而重发。研发测试和真实验收使用不同目录、明确的synthetic标识。
- 计划调整必须说明新证据及受影响验收项；两种模式同时交付、已有书优先和独立真实验收是本轮已锁定的用户选择。
